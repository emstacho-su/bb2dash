## 2. R-38 · Stream material posts are what each registered crawl added or changed

**Practice.** This is a slowly-changing-dimension / change-data-capture problem: detect new-or-changed rows between two snapshots and materialize only the delta as a feed event, keeping the full history append-only rather than mutating a "latest" row in place. The standard shapes are SCD Type 2 (a new row per change, keyed by validity range) and a CDC-style "before/after" delta computed with a CTE ([Streamkap, *CDC Soft Deletes and Tombstones*](https://streamkap.com/resources-and-guides/cdc-soft-deletes-tombstones); [CYBERTEC, *Tracking changes in PostgreSQL*](https://www.cybertec-postgresql.com/en/tracking-changes-in-postgresql/)) — this repo already has a working instance of exactly this shape in `bb_gradebook` (append-per-run, keyed `(run_id, course_id, column_id)`, DECISIONS 2026-09-15), which the requirement's own "still missing" section already points at as the template. **OSS.** [max-norin/pg_history](https://github.com/max-norin/pg_history) — a small Postgres extension that materializes an append-only history row per detected change via trigger; worth reading for its "detect a real change, not a touch" comparison (it diffs specific columns, not the whole row) rather than adopting the extension itself (D-19-adjacent: this project hand-rolls SQL, not extensions, for anything beyond `pgvector`/`pg_cron`/`pg_net`). **Pitfall.** An append-only history table with no retention rule grows unbounded — `bb_raw` already has this exact gap today (noted in the requirement's own "Notes"), so building the new history table without at least an index on `(course_id, run_id)` and a documented (even if "keep forever for now") retention line repeats a known mistake rather than fixing one. **Stack.** New table shaped like `bb_gradebook` for `bb_content`/`bb_files`, built inside `stage_content`/`stage_files` (Phase 8/9 functions) rather than a fresh stage; `v_course_stream`'s material arms rewritten to read only rows whose run matches the diff table's newest-registered-crawl predicate (reusing 043's pattern per the "Must respect" line); `web/src/lib/course-dimension.ts` `CourseStreamRow.meta`. **Size/seams.** L; ## 3. R-39 · Classwork shows Blackboard's current folder tree, without stale or duplicate nodes

**Practice.** Hiding a row Blackboard no longer reports while keeping its data (rather than deleting it) is the standard soft-delete/tombstone shape, and the standard failure mode is exactly the one already spotted here: keying on a compound natural key `(course_id, path)` means a rename looks like "old row missing + new row appeared" instead of "one row moved," because the natural key drifted under it ([Nilus, *Soft Deletes vs Hard Deletes*](https://www.nilus.be/blog/soft_deletes_vs_hard_deletes_in_data_architecture/); the general ETL lesson that a natural key is only stable until the source renames the thing it identifies). ## 5. R-41 · Home names interrupted, partial and stale syncs and a stopped scheduler

**Practice.** This is a dead-man's-switch problem: a process that should tick every N minutes and, if it stops, must be detected by absence rather than by an error it never got to raise. The standard shape is a heartbeat table a job stamps on every run (success or not) plus a *reader* that classifies age into stages — `healthy` → `late` → `missing` — with a grace period between stages, not one hard cutoff, because a single 2-minute-late tick under load is a different fact from a scheduler that died an hour ago ([crontap, *Dead man's switch, explained for developers*](https://crontap.com/blog/dead-man-switch-explained-for-developers); [upti.my, *Designing heartbeat monitoring*](https://www.upti.my/blog/designing-heartbeat-monitoring-system)). **OSS.** [mccabetrow/dragonfly_civil `supabase/migrations/20251231200000_reaper_heartbeat.sql`](https://github.com/mccabetrow/dragonfly_civil/blob/c9aec6eb1f6cde2013c7f7bafc80f6d3f668fceb/supabase/migrations/20251231200000_reaper_heartbeat.sql) — a real Supabase/pg_cron project shipping almost exactly this shape (`ops.v_reaper_status` view over `last_run_at`, granted to `service_role`, read by the app layer); borrow the "one small status view a pg_cron job stamps, one client read" split, not the table names. **Pitfall.** The requirement's own "Still missing" already proposes a single "warn after 10 minutes" threshold; the OSS pattern argues for two stages (e.g. `late` at 1 missed tick ≈ 2–4 min, `missing`/`stuck` at 5+ missed ticks ≈ 10 min) so Home can say "running a little behind" before it says "the scheduler looks stopped" — a single threshold conflates a normal jitter with a real outage. **Stack.** `v_sync_status` (add notes/stage, not a redefinition of `freshnessLine`'s existing per-class thresholds), a new small heartbeat read shared with R-52 (see research-added, below) rather than two separate ad hoc checks; `db/tests/phase9_transform_states.sql` for the partial/reaped fixtures; `NeedsAttention.tsx`, desktop `reducer.ts` copy. **Size/seams.** L (run-states S–M, thresholds+heartbeat M, per the requirement's own split); ## 7. R-43 · ?item= popout URLs load without a React #418 hydration error

**Practice.** React error #418 is specifically a text/DOM hydration mismatch — "the markup rendered by the server does not match what the client produced on hydration," and React discards and re-renders the affected subtree client-side ([react.dev/errors/418](https://react.dev/errors/418)). The standard fix when the mismatch source is a persisted client-only cache (exactly this repo's `PersistQueryClientProvider`) is a hydration gate: render one fixed placeholder on both the server pass and the client's *first* pass, and only switch to real content once `useSyncExternalStore` reports the client has mounted — the `getServerSnapshot` argument exists precisely to pin the SSR value ([tkdodo, *Avoiding Hydration Mismatches with useSyncExternalStore*](https://tkdodo.eu/blog/avoiding-hydration-mismatches-with-use-sync-external-store)). This repo already has this exact hook (`use-hydrated.ts`, used by `/planner` since the 2026-09-16 DECISIONS row); the fix is calling it from one more place, not inventing anything. **OSS.** Three independent, unrelated codebases converge on the identical four-line implementation this repo already has — [PeerDB-io/peerdb `ui/app/utils/useHydrated.ts`](https://github.com/PeerDB-io/peerdb/blob/0a71f63ac20a11fd57693217da2c3c36c2b4cb60/ui/app/utils/useHydrated.ts), [Southclaws/storyden `web/src/utils/useHydrated.ts`](https://github.com/Southclaws/storyden/blob/3bff5c4fc46244dd024e3861a7e3b2ce9befd1de/web/src/utils/useHydrated.ts), [assistant-ui `apps/docs/hooks/use-hydrated.ts`](https://github.com/assistant-ui/assistant-ui/blob/da9a624496ae97864ae30e90f85c7533092a228d/apps/docs/hooks/use-hydrated.ts) — all `useSyncExternalStore(subscribe, () => true, () => false)`. This is strong external confirmation that the repo's existing hook is the idiomatic shape, not that a different one is needed. **Pitfall.** Gating the *wrong* boundary — TanStack's own hydration-mismatch discussion notes the failure mode where "the client status starts off immediately as success," i.e. gating too narrow a component leaves a sibling still reading the warm cache before hydration ([TanStack/query#5357](https://github.com/TanStack/query/discussions/5357)). The requirement's own plan avoids this correctly (gate `ItemPopout` itself, before its early return, not each panel separately) but the same pitfall applies to `AssignmentDetailBody`, which is shared with the un-Suspended `/course/[id]/assignment` page — gating that shared component too would show a placeholder flash on a page that was never broken; the fix belongs only in the popout wrapper, confirmed correct as scoped. **Stack.** `web/src/components/popout/ItemPopout.tsx` (add the gate before line 39's early return), `AssignmentPopout.tsx`, `SessionPopout.tsx`; `use-hydrated.ts` reused, not modified; hydration test per `?item=` kind cloned from `PlannerWeek.hydration.test.tsx`'s template. **Size/seams.** S; should land before R-37 (more `?item=` link traffic should not launch into a live bug). **Changes.** None to scope — confirms the plan precisely and adds the `AssignmentDetailBody` non-gating note as an explicit Contract line so a worker doesn't "helpfully" widen the gate.

## 11. R-48 · Web app shows grade-posted and due-tomorrow notices, or the clause closes

**Practice.** Running the same alert on two channels (a desktop toast and an in-app feed) for the same event is a known source of notification fatigue, and the standard remediation is channel consolidation, not duplication — alert-fatigue literature is consistent that redundant delivery of the same signal degrades trust in *both* channels, not just the redundant one ([Datadog, *Best practices to prevent alert fatigue*](https://www.datadoghq.com/blog/best-practices-to-prevent-alert-fatigue/); industrial alarm-management guidance recommends roughly one alarm per ten minutes per operator during normal operation as the ceiling worth designing toward, [Tractian](https://tractian.com/en/blog/how-to-prevent-alert-fatigue-in-condition-monitoring)). ## 13. R-51 · Web tests and lint describe the app and run reproducibly

**Practice.** Two independent, unrelated best-practice threads apply here. First, coverage scoping: `coverage.include` should track what is *tested*, not be a hand-maintained allowlist that silently drifts as new suites are added — vitest's own coverage model treats `include` as a filter over instrumented files, so a stale list simply hides untested files from the report rather than protecting anything, which is exactly the drift the requirement diagnoses (60 suite-driven modules unmeasured). **Practice.** `REFERENCING OLD TABLE` on a statement-level `AFTER DELETE` trigger is the standard, documented Postgres mechanism for exactly this shape (act once per statement on the *set* of deleted rows, not once per row) — the feature has existed since Postgres 10 and is unrelated to Postgres 17-specific behavior, so nothing here is version-sensitive ([PostgreSQL docs, `CREATE TRIGGER`](https://www.postgresql.org/docs/current/sql-createtrigger.html)). **OSS.** Three independent, mature codebases ship the identical shape the requirement proposes — [kvesteri/postgresql-audit `audit_table_stmt_level.sql`](https://github.com/kvesteri/postgresql-audit/blob/0ad84571a56e03102c49cbeccdbe3a3c01e8a287/postgresql_audit/templates/audit_table_stmt_level.sql) (`AFTER DELETE … REFERENCING OLD TABLE AS old_table FOR EACH STATEMENT`), [LemmyNet/lemmy `crates/diesel_utils/replaceable_schema/utils.sql`](https://github.com/LemmyNet/lemmy/blob/646f5a01558d5a38859558426ce54b06185b92e2/crates/diesel_utils/replaceable_schema/utils.sql) (a production federated-Postgres app using the same trigger for cascade cleanup), and [bantling/tools `0040-create-table.sql`](https://github.com/bantling/tools/blob/cb15539c73750ce63a23cc54db5ec0ba98ebe7e6/postgresql/json/scripts/0040-create-table.sql). Borrow the shape (one statement trigger, one transition table, one `DELETE … WHERE id IN (SELECT DISTINCT series_id FROM old_table WHERE series_id IS NOT NULL AND NOT EXISTS (…))`), not any of their code verbatim. **Pitfall.** The requirement's own "Seams" note is already correct and matches a known gotcha in this exact pattern: a statement trigger's `old_table` reflects rows deleted *by that statement*, so when the 083/088 RPCs' own inner `DELETE` fires this trigger first, the RPC's *own* subsequent series-delete step will then match 0 rows — this is expected, not a bug, and TR-4 must be re-run under the new trigger to confirm zero duplicate work, exactly as already planned. **Stack.** New migration (091+, outside Phase 14's 091-099 block) adding the trigger to `planner_events`; `search_path` pinned `public, pg_temp`, not `SECURITY DEFINER`, revoked from `public`/`anon`/`authenticated` per the 082 convention; rolled-back SQL test extending `db/tests/phase12b_082_083_planner_series.sql`'s existing TR-4 fixture rather than a new file. **Size/seams.** S; no other seams beyond what the requirement names. **Changes.** None — the requirement's plan is already exactly the standard-practice shape; this research's only contribution is external confirmation (two production OSS codebases use the identical trigger form) that de-risks the design choice.

## 20. S2-home-1 · upcoming work scrollable

**Practice.** A horizontal scroll strip needs three independent input paths to be reachable by every device class: native touch swipe, trackpad two-finger horizontal swipe (both work automatically with `overflow-x: auto` because trackpads report a native `deltaX`), and — the one every naive implementation misses — a plain vertical mouse wheel, which has no browser-native mapping onto horizontal scroll at all and must be converted in JavaScript (`deltaY` → `scrollLeft`), plus click-and-drag for a mouse, which is likewise not a native browser behavior on a scroll container. This repo's own `UpcomingTracker.tsx` confirms the gap directly: `UpcomingTracker.module.css` sets `overflow-x: auto` (line 64) and the component drives `scrollerRef.current.scrollLeft` only programmatically (for the anchor/◂▸ logic); there is no `onWheel` or pointer-drag handler in the file. So a trackpad user or the ◂/▸ buttons already work (matching 12b's H-2 front-end check, "wheel / drag scrolls," which was verified for the input methods tested), but a plain mouse — no trackpad, no touch — gets nothing when it wheels over the strip, which reads exactly like "not scrollable." **OSS.** [studio-nordwerk/scroll-carousel](https://github.com/studio-nordwerk/scroll-carousel) — a dependency-free carousel built "CSS scroll snap first," with drag as an explicit opt-in *progressive-enhancement* plugin layered on top of native scrolling rather than replacing it; borrow the layering idea (native scroll stays the baseline, wheel/drag are additive, never a JS reimplementation of scrolling itself). [Muse-software/muse-software `lib/useHorizontalScroll.ts`](https://github.com/Muse-software/muse-software/blob/a0e611546bd71e36eb8d9fa9fdea037236b0f1bb/lib/useHorizontalScroll.ts) — a small React hook adding exactly the missing `wheel` listener (`removeEventListener("wheel", handleWheel)` visible in the fetched fragment) around a scroll track ref; borrow the hook shape (attach/detach on the track ref, convert `deltaY` when `deltaX` is ~0, leave native `deltaX` alone so trackpads are untouched). [Grsmto/scroll-snap-carousel](https://github.com/Grsmto/scroll-snap-carousel) — adds drag-to-scroll as a layered addition to native `overflow-x`; borrow the "drag only kicks in on `pointerdown` + move past a small threshold" gesture, so a click that was meant to open a due item (the tracker's cards are already clickable, per 12b's "keep the buttons as well") is not swallowed by the drag handler. **Pitfall.** A drag-to-scroll handler that does not distinguish a click from a drag will break the tracker's existing click-to-open behavior — this is the single most common bug in every drag-scroll implementation surveyed, and the fix (a small pixel-distance or time threshold before treating pointer movement as a drag) must be a named acceptance check, not an afterthought. **Stack.** `web/src/components/tracker/UpcomingTracker.tsx`/`.module.css` (`scrollerRef`); a new shared hook (see research-added, below) rather than an inline handler, since the same gap likely recurs anywhere else `overflow-x: auto` is used without a wheel handler. **Size/seams.** S; no migration; can ship independently of S2-home-2. **Changes.** Turns a vague "make it scrollable" ask into a precise, three-line diagnosis (wheel + drag both missing for mouse users; touch and trackpad already work) with a named regression risk (click-vs-drag) — see the research-added question below on whether this, or a genuine touchpad/trackpad regression, is what Stack is actually hitting.
