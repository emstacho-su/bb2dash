## Chunk shape (matters for embeddings)

`bb_file_text` units are extraction-native, not embedding-sized:

| unit_kind | rows | avg chars | max chars | >8k chars | <200 chars |
|---|---|---|---|---|---|
| slide | 295 | 308 | 1,523 | 0 | 108 |
| page | 219 | 3,330 | 9,568 | 7 | 2 |
| doc | 17 | 6,729 | 24,865 | 5 | 0 |
| sheet | 3 | 4,957 | 5,072 | 0 | 0 |

Implication: 12 units are too long to embed whole (the `doc` units are entire syllabi), and 108
slide units are trivially short. The embeddings table therefore keys on
`(text_id, model, part_no)` so long units split into parts at embed time and short slides can be
merged upstream later without schema change.

## Open decisions / gaps

1. **Embedding model.** Column is `vector(1024)` sized for Voyage `voyage-3.5` (Anthropic's
   recommended embeddings provider). If you'd rather use OpenAI `text-embedding-3-small`
   (1536-dim) or similar, it's a one-line alter while the table is empty — decide before the
   first embed run.
2. **Embedding job doesn't exist yet.** 534 units, ~175k chars of long-tail — one cheap batch
   run once the model is picked.
3. The one `na` file (IST.466) and the image-only IST.352 instructor bio PDF have no text; OCR
   is the only route if they ever matter.
4. `bb_content.body` (Ultra document bodies) is now FTS-indexed but not in the embedding path;
   add `bb_content` rows to the embed job if hub retrieval should cover page text, not just files.

## Docker verdict (asked in this task)

Not needed for what's built here. Postgres + pgvector already run managed inside Supabase — a
container would only duplicate that. Docker earns a place in exactly two futures: (a) a local
dev copy of the stack (`supabase start` runs the whole stack in Docker — useful once the
dashboard app needs offline/isolated testing against a throwaway DB), or (b) self-hosting an
embedding model instead of calling an API (not worth it at 534 chunks). Skip it for now.
